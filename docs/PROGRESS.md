- 2026-11-15, slice 4 eventbus: backend/src/eventbus/. Inject `EVENT_BUS` (from `EventBusModule`, not in AppModule yet; Sessions should import it). One channel `picplease_events` carries every event as `{n, p}`; publish is `SELECT pg_notify` on `tx` or the pool, so a rolled-back transaction never delivers. - 2026-11-19, web W3: web/src/camera.ts and compressor.ts. No new dependency: the camera, video element and canvas are passed in, so tests use fakes and run in the node environment (no jsdom); real encoding is checked on devices in W7. Choices made in this slice (confirm or change): constraints are `facingMode: { ideal: 'environment' }` with ideal 1920 x 1080 and no audio (ideal, not exact, so a laptop or a phone without a rear camera still works); NotAllowedError and SecurityError are `denied`, every other failure (no camera, busy, overconstrained, no getUserMedia outside a secure context, viewfinder that will not play) is `unavailable`, both lead to noCamera with `state.cameraProblem` set (new field) so W5 can word them apart. The frame is drawn once straight from the video into a canvas already scaled to 1920 px on the longest edge (no full-size copy, which matters for iOS Safari's canvas memory cap) and the canvas is released after encoding. Quality 0.7 first; if the JPEG is over `limits.maxPhotoBytes`, 0.5 then 0.35, else CompressError. A browser that returns something other than image/jpeg from toBlob is refused (CompressError). A canvas re-encode has no EXIF, so no location leaves the phone; stream frames are already upright. Encoding runs on the main thread (toBlob is asynchronous in browsers); OffscreenCanvas in a worker can come later if devices stutter. Web tests 5 and 15 covered (73 tests).
- 2026-11-19, web W4: web/src/uploader.ts. `add(frame)` answers `accepted`, `full` (limit reached, shutter stays disabled until `canShoot`) or `stopped`; `whenIdle()` resolves when nothing is in flight (for Done); `finish()` and `end()` let lifecycle and realtime stop it from outside. Choices made in this slice (confirm or change): issue and confirm retry passing errors (NETWORK, RATE_LIMITED, INTERNAL_ERROR; plus UPLOAD_LIMIT_REACHED for issue and INVALID_REQUEST "object not there yet" for confirm) after 1, 2, 4, 8, 15, 15, 15 s (about a minute), then the photo counts as failed; the PUT retries the same URL after a network error or 5xx (1, 2, 4 s) and gets a new URL after a 4xx (expired or refused signature) or when those retries run out, up to 3 new URLs, matching the mobile helper; PUT timeout 60 s, `credentials: 'omit'`, no Authorization header. SESSION_FINISHED stops new photos (`finished`: photos without a URL are discarded, the ones with a URL still upload and confirm, since confirm is allowed in finished); SESSION_GONE or UNAUTHORIZED (the helper token is refused once revoked, expired or closed) is `gone`: every PUT is aborted and nothing more is sent. Discarded photos count as neither sent nor failed. NOT_FOUND on confirm (the server discarded the photo) counts as failed with no retry. Known cost: if compression fails after the URL was issued, the server's pending photo holds a slot until Jobs' stale-upload sweep (URL expiry + 60 s). The R2 CORS rule allowing PUT from https://picplease.app (owner, "To confirm") is needed before this works in a browser. Web tests 6 to 9 covered (87 tests).
